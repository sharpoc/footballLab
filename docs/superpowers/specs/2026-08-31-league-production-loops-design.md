# 联赛日常刷新与赛后公网同步设计

状态：用户已确认设计；第一份“日常赔率刷新与可靠发布”已完成本地离线实现和回归，仍未获准 live、定时器安装、提交推送或部署。第二份赛后公网同步仍未在本阶段实现。

## 1. 目标与证据边界

解决两项独立问题：未出现正式首发时也能按计划生成有效赛前首选；严格确认完赛后，比赛退出公网实时列表并进入可追溯的历史记录。

2026-08-31 的只读预检发现：五联赛正式 snapshot 仍为 8 月 25 日，公网 73 场均为 `NO_CLEAN_MARKET`，47 场已过开球时间。日常 scheduler CLI 只开放 dry-run；首发 observer 不能代替日常刷新；FotMob postmatch runner 没有公网发布入口。47 场是待查赛果，不是已确认完赛。

当次日常 dry-run 选中意甲、西甲、英超、巴甲，胜平负方案估算 4 credits；这不是完整盘口预算或以后运行的价格保证。五联赛 FotMob 赛后输入通过当次只读验证，德甲仍未 active。上述事实须在真实执行前重新验证。

## 2. 方案与交付拆分

采用复用现有采集、预测、结算、HMAC ingest 的方案，不重写模型，不新购 provider。分两份实施计划、独立 PR 和独立验收：

1. 日常赔率刷新与可靠发布：独立于首发，先解决推荐过期；不依赖赛后正式启用。
2. 严格赛果的公网同步：复用已接受结果，补齐结果可见性与历史投影；正式运行保持六联赛 Gate A 前置要求。

手工刷新只作为另行批准的临时运维操作，不代替定时生产链路。仅按日期隐藏比赛不予采用，因为它会误删延期、未确认赛果以及仍需审计的事件。

## 3. 不变量与范围

- 范围为固定六联赛；世界杯、中超的调度、数据、统计和通知保持独立。
- 每场有有效可结算盘口即输出唯一 schema v2 `MATCH_PICK`；没有有效盘口才为 `NO_CLEAN_MARKET`。不改 `match_pick_v3`、模型参数或 club rating pending 语义。
- 正式首发不是日常推荐前置条件；首发后复核继续走现有 observer，严格 confirmed 判定不放宽。
- `active` 必须验证证据指纹和严格 identity；不以字符串或 slug 代替。日常刷新按已验收联赛运行，不伪造德甲资格。
- 赛后正式 live/write 仍要求六联赛 Gate A 全部完成，再逐项授权 Gates B–D。五联赛 dry-run 通过不自动改写该门禁。
- 不事后生成 closing，不把 reconstructed、legacy、世界杯或中超混入六联赛正式统计。不删除或静默改写已接受比分。
- 仅供研究分析，不构成投注建议，不输出金额、追损或串关建议。

## 4. 子任务一：日常赔率刷新与发布

### 4.1 职责分配

以 `league_scheduled_publish` / `league_live_planner` 负责只读 due 决策和日常编排，复用 `league_batch_runner`、`league_odds_refresh` 的正式采集与分区提交能力。生产 CLI 显式区分 dry-run、live/write 和发布，真实运行使用系统时钟，禁止用重放时间触发 live。

生产赛程来源为严格校验过的近期赛事发现缓存和正式 snapshot；`data/probe/.../events.json` 仅作为验收样例，不能永久承担生产发现。新发现的队伍未进入严格 registry 时隔离并报告，不绕过身份校验。赛事发现使用已验证的 provider 契约；现有样例不足以覆盖的接口必须独立 probe 后才实现 live 解析。

### 4.2 Due、额度与并发

保留 T-6h、T-90m、T-25m 和正常额度下 `valid_until - 20 分钟` 的刷新意图。同联赛同轮请求合并，盘口取本轮所需集合，估算与实际 fetch 参数必须相同；不能计划 h2h 却实际抓三类盘口。过期保底不能覆盖 T-25 所需盘口集合。

持久保存成功刷新时间、锚点完成与 pending 状态；相同锚点/相同证据不会每次唤醒重复消费。无未来赛事时仍需有有界的发现计划，不能因为旧列表为空永久停止发现。最短间隔、发现周期和每日预算作为第一份实施计划的显式策略参数提交审核，不在本文件授权安装任意频率的定时器。

复用五个显式 key 槽位轮换，剩余不高于 30 时保留应急余额、优先下一可用槽位；全部无新鲜额度按既有低额度策略降频，全部耗尽停止刷新。不能将多个槽位或 legacy 汇总行的余额重复累加。实际费用以响应 header 入 ledger，失败请求不能假定免费。

日常刷新与首发后刷新必须协调同联赛写入、quota 和发布，防止并发重复抓取、覆盖较新 snapshot 或丢失 closing。锁顺序和崩溃恢复在实施计划中逐项定义并测试，不得只给两个 runner 各加一把互不相关的锁。

### 4.3 提交与发布

读取正式 acceptance/identity → 生成计划 → live 门禁及锁 → 重新检查时间/额度/身份 → 抓取并校验 → 原子提交分区、归档 observed snapshot → 聚合 → 持久 pending → HMAC ingest → 验证 `stored/duplicate` → 记录回执并清 pending。

pending 绑定 endpoint、payload hash 和完整 component 指纹；重试使用已提交内容，不再次抓赔率。重试过期 pending 不得令线上较新 component 回退，必须由共同发布顺序和组件版本验证拒绝旧发布。pending 失效时显式保留审计结果，再按新计划处理，不能静默丢失。

坏分区保留最后已知良好数据并明确 stale/blocked；不将旧缓存冒充本轮新鲜数据。归档必须保留实际生成时间，赛后不得把重建的旧推荐标成 observed。公布成功与通知成功是不同状态；本子任务不新增每轮推荐群发。

provider 单轮响应遗漏旧事件不构成取消或完赛证据。客户端必须保留上一版未被本轮覆盖的公开事件及其逐场 `source_snapshot_id`；同一 `event_id` 的开球时间或主客队严格身份变化必须阻断。服务端在 SQLite 同一事务内验证 odds component 的事件 membership 只能保持或扩张，拒绝较新时间戳包装的删场或身份改写。只有第二份计划引入的严格 terminal/result component 才能证明比赛应退出实时列表；因此第一份计划不会仅凭 provider 漏场或时间经过删除比赛。

## 5. 子任务二：赛后结果与公网可见性

### 5.1 数据来源与投影

复用 `league_postmatch_runner` 及 result receipt、closing、postmatch、components/statistics。FotMob calendar/detail 必须严格证明 FT、90 分钟比分一致、timezone-aware kickoff、身份一致且无加时/点球/aggregate。缺失、冲突、比分修订保留旧结果并隔离，不按已过开球推断 FT。

公网需要区分“已确认赛果”和“可结算推荐”：所有合法已接受 FT 都可退出实时列表；只有合法 observed closing 才能进入正式推荐战绩。缺 closing 的历史记录明确为缺少赛前记录，不能构造 `MATCH_PICK` 或用 `NO_CLEAN_MARKET` 冒充当时实际决策。

现有 `query.project_match_rows` 根据 `finished.matches` 隐藏比赛，但现有结算 matches 不能覆盖缺 closing 的全部 FT。第二份实施计划必须同时定义完整结果身份集合及历史投影契约，验证跨联赛身份、不依赖展示队名，并明确旧 snapshot 无新字段时的兼容行为；不能只向现有统计列表塞入假 closing。

### 5.2 发布边界

赛后发布使用独立派生产物和 pending/state，不能覆盖赛前 odds snapshot、消耗 The Odds API 额度或清空其他联赛数据。日常、首发后、赛后对同一公网联赛视图的发布必须通过统一的组件版本合并/单调校验边界；仅靠不同 run_id 幂等不足以防止旧赛前聚合覆盖新完赛结果。

第一份计划须预留并测试发布版本保护；第二份计划落实结果组件的单调合并。最终 API 必须同时保留最新有效赛前组件和累计合法结果组件。部署新的字段读写契约前先验证旧数据兼容，不改数据库 schema 的方案优先；若确需迁移，须另行确认。

公网发布失败不回滚已接受赛果或本地结算，保留可恢复 pending；只有 ingest 成功并通过公网 GET 验证对应比赛退出实时列表，才可报告该轮“公网关闭成功”。服务回执不能替代网页验收。

### 5.3 调度与通知

赛后 timer 继续固定北京时间 10:30 / 16:30、`RunAtLoad=false`，与首发 observer 的五分钟唤醒无关。本设计不承诺终场后即时下架：未被严格确认并发布前展示赛果待确认。若用户需要终场后分钟级更新，须独立修改频率和成本设计。

保持赛后通知 outbox 的 pending 优先和失败不回滚结算语义；WxPusher 接受成功不等于用户已阅读。发送成功到回执持久化之间仍有 at-least-once 重复窗口，不能声称 exactly-once。上线先静默，真实通知另行授权。

## 6. 可验证验收标准

| 场景 | 必须验证的结果 |
| --- | --- |
| 首发一直缺失、赔率合法 | 日常链路仍生成并发布有效唯一首选 |
| 首选即将过期 | 正常额度下计划及时刷新，不能依赖首发触发 |
| 同轮多比赛、重启或两个 runner 并发 | 按联赛合并请求；不重复消费已完成锚点、不丢新 snapshot/closing |
| provider/发布失败 | 明确 stale/blocked 或 pending；发布重试不重复抓赔率 |
| 无未来缓存赛事 | 有界发现可纳入真实新赛程；unknown identity 仍隔离 |
| 比赛过时但无严格 FT | 保留赛果待确认，不直接下架 |
| 严格 FT 且有合法 closing | 正确结算、历史可追溯、公网实时列表移除 |
| 严格 FT 但缺 closing | 可关闭比赛；明确缺记录，不补造首选、不进入命中率分母 |
| 旧赛前发布晚于赛后发布到达 | 不复活已确认完赛比赛、不回退任何较新组件 |
| 单联赛损坏或比分修订 | 保留 LKG、隔离错误；不清零其他健康分区 |
| 默认 dry-run | 不读 secret、不联网、不建业务锁、不写数据、不通知；相关 manifest 不变 |

离线测试以保存的真实样例为基础；注入式 fake 只模拟请求与发送边界，不代替 provider 契约证据。实施后运行项目完整测试，并在获得独立授权后分别核验真实费用、ingest receipt 和公网结果。

## 7. 阶段授权与回滚

1. 当前仅写设计文档及近期记录；文档审核后再分别写两份实施计划。
2. 本地实现、测试和文档更新：独立确认，使用隔离 worktree，保留运行目录未提交记录。
3. commit/push、PR、merge、部署分别遵守项目授权；不得借文档批准修改线上状态。
4. 真实赔率首次运行须重新列明 active 集合、实际 markets、quota 槽位状态、费用估算、写入与发布范围。
5. FotMob 赛后 Gate A 六联赛完成后，方可申请静默 live/write；安装 timer、首次真实通知仍独立确认。
6. 数据契约部署先于生产写入；本机定时器代码同步与 ECS 部署分别验收。
7. 回滚只停用对应新 timer/切回已验证代码或 release，不删除接受结果、closing、pending 和审计记录；旧代码不兼容新产物时保持任务停用，不强行恢复旧写入。

## 8. 对抗性自审

- **已修订：仅加定时器不足。** 当前 CLI 为 dry-run，缺生产依赖和状态恢复；实施计划必须覆盖真实入口与恢复，而非安装即完成。
- **已修订：4 credits 不是预算。** 计划与 fetch 的 markets 必须一致，重试、发现、多槽位共享成本分别核对。
- **已修订：结算列表不等于完赛集合。** 缺 closing 的真实 FT 必须可退出实时列表，但不得污染正式战绩。
- **已修订：HMAC 幂等不防数据倒退。** 旧赛前 payload 与新赛后 payload 的覆盖反例必须成为端到端回归。
- **门禁保留：五联赛通过不等于六联赛 Gate A 完成。** 不在设计中偷换激活范围；真实运行前重新核验德甲证据。
- **剩余风险：公开源可滞后或变更，免费额度可不足。** 保留明确降级与审计，不承诺每场都有新鲜赔率或即时赛果。
- **剩余风险：缺失历史 closing 不可修复为真实历史推荐。** 积累未来合法样本，不用小样本调参，也不以删除低置信场次提高命中率。

结论：设计将真实生产链路与本地能力分开，拆成两份计划；没有授权 live 的隐含步骤。实施计划必须进一步固定调度参数、锁顺序和公开字段契约，若偏离本设计或需要迁移，应重新提请确认。
